# Grokbot "Research" report 3: sim settings for stable small-object pinching

Condensed from the bot's reply, 2026-11-14 ~02:20. UNVERIFIED unless marked **checked** (I confirmed in source myself). "Own calc" = bot's arithmetic. Nothing built. Pad-material and PD-unit parts of the job were partly answered here; real pad material is still unknown.

## Bottom line (bot)
Biggest, best-evidenced fix: enable `solve_articulation_contact_last`. Then turn on twisting friction (currently zero), fix the "max" friction combine mode, and cap the sim hand torque. Step-test gains first because an open Isaac Lab bug may already make sim stiffness 100 behave like the real kp 1.5.

## Findings, most applicable first
1. **Solver ordering.** With `physxScene:solveArticulationContactLast` off (default), "the closing target is re-imposed through the object". Turning it on cut jaw penetration from +14.88 mm to -0.64 mm on a 34 mm cylinder and +17.41 to -0.87 mm on a 34 mm box; the grasp held instead of dropping, CPU and GPU (IsaacLab PR #6357). Field: `PhysxCfg.solve_articulation_contact_last`, added in isaaclab 0.46.5. Whether the installed version has it: UNVERIFIED.
2. **Twisting friction** lives on collision properties, not the material: `PhysxCollisionPropertiesCfg.torsional_patch_radius` and `.min_torsional_patch_radius`, in metres; zero radius means no torsional friction (Isaac Lab `schemas_cfg.py`). USD attributes `physxCollision:torsionalPatchRadius` / `minTorsionalPatchRadius`, default 0. The `sim_utils.CollisionPropertiesCfg` the repo uses should inherit both (UNVERIFIED). Use the min radius (the torque from `torsional_patch_radius` scales with penetration depth, so with `rest_offset=0` it may barely act). Values found: 1e-3 m on a 3 cm cube (Isaac Lab discussion #2651). DeXtreme/DexPBT/HORA configs set none.
3. **Dex3 actuators in unitree_sim_isaaclab** (**checked**, see log): `ImplicitActuatorCfg`, stiffness 100, damping 10, armature 0.1, effort_limit 300, velocity_limit 100, no joint friction, self-collision off; starter repo does not override. Real hand 1.4-2.45 Nm (**checked** `joint_spec.yaml`). **The sim forwards only position targets, so kp/kd sent over DDS are ignored** (`action_provider_dds.py`, bot, not checked).
4. **PD units unresolved, possible bug.** No Unitree doc states joint-side vs motor-side units for Dex3 kp (gear ratios 1:108 and 1:214). Isaac Lab issue #4918 (open) reports implicit-actuator joints 50-57x softer than stated (apparent degree/radian slip); a maintainer called it "plausible". If it applies, stiffness 100 behaves like about 1.75 N·m/rad, close to the real 1.5. UNVERIFIED. NVIDIA's gripper-tuning guide also warns USD vs PhysX stiffness units differ by 180/pi. Comparison: Isaac Lab's G1-Inspire hand uses stiffness 10, damping 0.2, effort 30; ProtoMotions Dex3 uses 0.5 (thumb root 2.0) and 0.1.
5. **Friction combine mode.** PhysX uses the higher of the two materials' modes (average < min < multiply < max). **Checked**: objects use "max" with 1.2 static (`scene_cfg.py:228`), so fingertip friction matters only above 1.2. Fingertip material: `spawn_rigid_body_material` + `bind_physics_material` on the thumb_2 / index_1 / middle_1 link prims, or `randomize_rigid_body_material` at startup. Compliant-contact fields exist but are off by default.
6. **Pad material and real friction.** Unitree does not publish it (EN/CN pages, support intro, disassembly manual); no teardown or X post found. "Rubber" appears only in a starter-repo comment. Closest measurement: PLA object vs a 0.6 mm TPU pad held 38-39 N pull-out vs about 10 N for PLA on PLA at about 15 N jaw force (Bialek 2023, MDPI), effective mu about 1.3 vs 0.33 (own calc). A 10-minute tilt test on the real pad would answer it.
7. **CCD and contact settings.** CORRECTION to my earlier note: **checked** `enable_ccd = True` and physics `dt = 0.005`, decimation 2 (`env_cfg.py:75-83`); but the bot says PhysX also needs a per-body `physxRigidBody:enableCCD` flag (default false) with no Isaac Lab config field, so the scene flag **probably does nothing for the objects** (UNVERIFIED). On GPU dynamics CCD is off anyway. Likely irrelevant: fingertips move about 1 mm per 5 ms step at the 3 rad/s cap, well inside the 4 mm contact offset (own calc). Reports: #3054 (dexterous hands need dt 1/120-1/200, we are at 1/200), #3001 (fingertip tunnelling, closed with no fix). Reference configs: Isaac Lab tuning guide says increase position iterations first (8-64, keep TGS); Dexsuite uses dt 1/120, 16 position iterations, friction DR 0.5-1.0, gain DR x0.5-2; DeXtreme/DexPBT/HORA use contact_offset 0.002, rest_offset 0.
8. **Other tricks.** NVIDIA's gripper guide: set stiffness to max torque divided by the closing error you want; with an implicit drive extra stiffness "will not result in the drive providing more force". Slower closing helped in forum replies, but one user saw slips even at mu = 10: sim grasp success is fragile.

## Bot's 5 sim parameters to change first
1. `PhysxCfg.solve_articulation_contact_last = True` if the version has it.
2. Object `min_torsional_patch_radius` and `torsional_patch_radius`: sweep 0.001-0.005 m, measure prism spin in the oracle.
3. Friction: object `friction_combine_mode="average"`, object mu 0.3-0.6, fingertip mu 0.8-1.3, randomise x0.5-1.5.
4. Dex3 actuators: step-test against real `hand_q` first (because of #4918), then cap `effort_limit` at about 1.4-2.5, fit stiffness (about 5-25 if #4918 does not apply), damping for no overshoot, randomise gains x0.3-3.
5. Position iterations 32-64, object `contact_offset` 0.002-0.004, `enabled_self_collisions=True` on the hands, optionally per-body speculative CCD.
